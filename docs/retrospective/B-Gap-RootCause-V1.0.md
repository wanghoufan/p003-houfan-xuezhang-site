## 1. 差距证据链七问（按影响排序）

### 差距一：作品展示站混入第三方推广内容，引发全域名 Safe Browsing 拉黑

1. **原来怎么说**：无任何记录表明 Day 1 讨论过"站上放什么内容"。首版需求只能从提交反推：个人展示 + 照片 + 项目。
2. **后来实际怎样**：08-03 服务区上线「GPT 代充值」（`e674ae3`），08-08 加「Claude Code 中转」（`6d6e1c8`）。2026-10-15 Google Safe Browsing 把整个 `wanghoufan.github.io` 域判为"欺骗性内容"，p002/p003/p006/posture-guard 全部报红（HANDOFF 2026-10-23 节）。
3. **差在哪里**：作品展示定位 ↔ 灰色代充值推广，性质冲突；且代价由全域名承担，不是单站。
4. **为何本应提前思考**：代充值/中转属平台明令打击的高危内容，任何一个面向公众的站点都不该默认放；这不是技术判断，是内容策略判断。
5. **不提前造成何种返工**：两次下架（`43751d3` 删中转、`1af6696` 删代充值，净删约 400 行 + 1.6MB 图）；整域名信任受损待申诉（HANDOFF 待办：Search Console 请求审核仍未完成）；`public/services/`、`ServiceCard.tsx`、专属测试全部废弃。
6. **下次普通人怎么说**："网站只放我的作品和联系方式，不卖东西、不放任何代充值/代购/推广外链。"
7. **提前明确的收益**：避免整域名被搜索引擎拉黑这一项目中唯一不可逆级损失，省掉申诉与两次下架。

### 差距二：技术形态与最终部署目标错位，构建层两次迁移

1. **原来怎么说**：首提交即用 ChatGPT Sites 的 vinext 全栈模板（`dbc1fcc`，含 `.openai/hosting.json`、`db/`、`drizzle/`、`examples/d1/`、`app/chatgpt-auth.ts` 86 行）。
2. **后来实际怎样**：最终是"无数据库、无登录、无后台"的纯静态站（README 自述），`output: "export"`（`430b9cf`）。
3. **差在哪里**：全栈模板 ↔ 纯静态，方向相反。
4. **为何本应提前思考**：静态作品站是可预见的最终形态（无用户输入、无数据存储）；Cloudflare D1/SIWC 从第一天就与需求无关。
5. **不提前造成何种返工**：vinext→Next.js 迁移（`0a5328b`）、静态导出改造（`430b9cf`）、GitHub Pages 接入与 basePath 条件注入（`4a170c4` `68f1867`）、残留文件拖到 10-03 才清理（`4830555`，9 文件）。
6. **下次普通人怎么说**："就是个纯展示网页，没有登录、没有数据库、没有人留言。"
7. **提前明确的收益**：一步到位纯静态，省两次构建层迁移与两个月模板死重。

### 差距三：内容规模从未一次盘清，作品墙靠多轮"对账"补齐

1. **原来怎么说**：无作品总清单记录；首版 `app/content.ts` 仅 85 行。
2. **后来实际怎样**：35 个作品，经由 8 → 14 → 23 → 27 → 35 的多轮补齐，且多轮提交明言"与 GitHub 主页清单对齐"（`8501c78` `ccf896a` `c75929f` `51c4158`）。
3. **差在哪里**：内容源从未被一次性枚举，靠事后发现缺再补。
4. **为何本应提前思考**：用户在 GitHub 已有主页作品清单，Day 1 盘点一次即可拿到全集。
5. **不提前造成何种返工**：约 10 个提交专门用于补条目（`8501c78` 单次 +279 行）；README 计数随之连错三次（14→23 修正 `ccf896a`、CLAUDE.md"8 个+2 服务"更正，见 HANDOFF 10-07 节）。
6. **下次普通人怎么说**："我的全部作品清单在这里（贴 GitHub 主页/表格），第一次就要全上墙，之后只增量加。"
7. **提前明确的收益**：内容一次到位，避免多轮对账提交与计数腐烂。

### 差距四：作品卡语义三次返工——访客该点哪里

1. **原来怎么说**：无记录；提交史显示卡片最初带标签区、350px 高、"项目档案"链接。
2. **后来实际怎样**：HANDOFF 记录用户三次纠正——卡片是"给访客看成果"不是档案入口（删文字/标题/封面三处档案链接）；"用户不关心你有什么标签"（删标签区）；"一页只显示 3 个不行"（3 列→4 列、摘要 3 行截断，8 卡一屏）。
3. **差在哪里**：开发者按"作品集归档"心智做卡片，用户心智是"橱窗"。
4. **为何本应提前思考**：卡片主行动是展示类站点的第一决策，问一句即可确定。
5. **不提前造成何种返工**：`43751d3` 单次大改 ProjectGallery/globals.css/content.ts；另有两个小返工同类——GitHub 链接文案缩短（`5de6d04`）、"打开网站"按钮措辞（`49f4398`）。
6. **下次普通人怎么说**："作品卡就是橱窗：点主按钮直接看成品（或下载），别的都不要。"
7. **提前明确的收益**：一次定稿卡片结构，省三次纠正与一轮布局量测。

### 差距五：首页信息架构反复——"方法与体系"开区又撤

2. **后来实际怎样**：10-07 新增首页"03 方法与体系"分区（`aeaa58c`，`Project` 加 `section` 字段、`ProjectCategory` 加 `template`）；**同日**按用户指正整体撤回，改为普通筛选标签 `method`，字段撤销（HANDOFF"更正上一条"节）。

4. **为何本应提前思考**：新区块是全局信息架构决策，应先问"这 2 件要不要和作品并列"。
5. **不提前造成何种返工**：单日内字段加→删、测试改两轮、GitHub 主页 README 分类同步移动（`23e9d94`）。
6. **下次普通人怎么说**："新增的东西先归进现有分类，不够放再说开新区块。"

### 差距六：外链健康无人管——死链贯穿全周期

1. **原来怎么说**：无外链清点记录。
2. **后来实际怎样**：至少四批死链——仓库改名 4 处（HANDOFF 10-03 节，`gh repo view` 核实）；分镜生成器 2 条访客点不开的死链（`36cc1ee`）；生活物种 Coze 付费墙链接（`7ff0ff6`）；封面图外链用改名前仓库名（`fe3a201`）。另 ChatGPT 临时域名、Coze 分享链接被标注"长期易失效"（HANDOFF"仍待用户处理"节）。
3. **差在哪里**：站上每一个对外 URL 都没有"发布前验证 + 持续巡检"机制。
4. **为何本应提前思考**：外部仓库改名、临时域名失效是高概率事件。
5. **不提前造成何种返工**：至少 6 个修复提交；项目 `siteUrl/releaseUrl` 字段体系（含"不为凑两个而编造链接"注释）在 10-03 才补建。
6. **下次普通人怎么说**："站上所有链接你逐个点开验证一遍；仓库要改名的先改完再上站。"
7. **提前明确的收益**：链接体系一次建对，杜绝访客撞死链。

### 差距七：视觉方向摇摆，主题体系三次成型

1. **原来怎么说**：无风格定调记录。
2. **后来实际怎样**：杂志编辑风（`d27b1f9`）→ 深色赛博朋克 redesign（`6d1e698`，参考外部 coze.site）→ 浅色主题需求 → 升级为三主题并存、默认深色（`dd2b4d1`，globals.css 增至 2400+ 行）；头像边框三日三改（`4c20e40`→`f3793b4`→`8874ffa`，最终"呼吸式发光"）。
3. **差在哪里**：风格按"参考别的站"逐次触发大改，而非 Day 1 定调。
4. **为何本应提前思考**：个人站的视觉身份是最典型的"用户心里有但没人问"项。
5. **不提前造成何种返工**：globals.css 三次结构性重写；三主题维护成本固化（HANDOFF 记录新增主题需改三处、漏白名单会首屏闪烁）。
6. **下次普通人怎么说**："风格照某个参考站来（给链接）；要浅色还是深色一开始就说。"
7. **提前明确的收益**：省一次 redesign 与一套主题的长期维护。

### 差距八：多语言后置

1. **原来怎么说**：无。
2. **后来实际怎样**：10-08~10-09 两批 i18n（`8767bed` 626 行、`6b8432e` 覆盖 27 件作品详情），且 README 最终口径"界面语言为中文"，英文仅同页切换。

7. **提前明确的收益**：内容录入一次双语，省逐条回填。

## 2. 责任区分

**用户合理应表达（不问就不该指望开发猜到）**
- 站上放什么内容、有没有代充值/推广类条目（差距一）。
- 作品全集清单与"全部上墙"的期望（差距三）。
- 卡片主行动：看成品 / 下载 / 看源码（差距四）。
- 视觉风格参考与明暗倾向（差距七）。
- 受众与是否要英文（差距八）。
- 部署在哪、国内打开速度要不要紧（`国内托管部署清单.md` 全篇均在补这一课）。

**顾问/计划者应主动发现（用户没说也必须追问）**
- 技术形态匹配：静态站为何带 D1/auth 模板（差距二）。
- 内容合规风险：面向公众站点 + 第三方付费外链的组合主动预警（差距一——用户未必知道 Safe Browsing 机制，顾问必须懂）。
- 外链清点：仓库改名、临时域名、平台分享链接的失效风险（差距六）。
- 内容源真值：GitHub 主页已有作品清单，应主动索取作为基线（差距三）。
- 首屏密度与卡片信息量预期（差距四）。
- 新增条目归入现有架构还是开新区块（差距五）。

**开发者负责解决**
- 纯静态导出、basePath 双线条件注入、`asset()` 外链前缀（`68f1867`）。
- button+window.open 弹窗拦截 → 原生 `<a>`（`ddf94d3`）——交互实现选型错误，属开发失误。
- 筛选条 flex-wrap 按假设宽度跳行（`9f4389d`）——布局计算靠猜不靠量测，属开发失误；修后 761-1440 档实测验证。
- 测试体系：死链钉桩、真点击回归（playwright-core + 本机 Chrome）、下架内容钉桩（HANDOFF 10-03/10-07 节）。
- 夹带提交交底：`9f4389d` 误带入另一会话 26 行样式（HANDOFF 10-07 节）——流程失误，事后如实留痕，处理得当。

**正常迭代（不能以事后知识苛责）**

**Agent/流程失误**

**部署与域名类专项根因**
- 双线（GitHub Pages + Vercel）来自"国内打开更快 + 镜像备用"的真实需求，但顺序颠倒了：先 Vercel 为主（08 月），09-29 才为国内托管改静态导出，10-06 才定 Pages 为主（`f6c3f05`）。根因：**部署目标与国内可达性要求在 Day 1 未问**。
- 验证通道缺陷：本机网络 `*.vercel.app` curl 全超时，生产验证只能走 `vercel ls` 看 commit SHA（HANDOFF"既有基础"节）——开工前未确认"部署后从哪验证"。
- 无自有域名：整域名信任捆绑在 `wanghoufan.github.io` 上，一次 Safe Browsing 判定殃及全部子站；`国内托管部署清单.md` 第六节已意识到"自有域名需 ICP 备案"但未推进。

## 4. 通俗需求表达问题（下次 Day 1 应说出的 10 问）

1. 这个网站只放作品展示和联系方式，还是也放付费/代充值/推广服务？（后者会触发搜索引擎封禁，强烈建议分开）
2. 我要上墙的作品一共 35 件，清单在这里（GitHub 主页/表格），第一次全上、以后只增量，行不行？
3. 访客点一张作品卡，最该去哪：打开在线版、下载安装包，还是看 GitHub 源码？没有的东西宁可不放按钮。
4. 作品按什么分类：网页/手机/桌面/方法体系？分类标准一开始定死。
5. 网站给谁看：国内朋友为主、海外也要、要不要中英切换？要英文的话作品介绍我中英一起给。
6. 视觉风格照这个参考站来（贴链接），深色还是浅色一开始定。
7. 首页一屏想看到几张作品卡？卡片上不要标签、介绍只要一两行。
8. 网站发布到 GitHub Pages，国内要能直接打开，部署后你从哪里验证给我看？
9. 我的照片、二维码、每件作品的封面图，开工前一次性给齐（比例：照片 4:3、封面 16:9）。
10. 站上每个链接（仓库、在线站、联系方式）你逐个点开验证；有仓库准备改名的，先改名再上站。
11. "已发布"的判定标准是什么：有在线地址/有安装包/只开源码？没达标的怎么标？
12. 内容改动只改一个文件（content.ts）就能生效，README 上的数字能不能自动跟着算？

## 6. 结论摘要

P003 的返工大头不是技术，而是**内容策略与内容规模未前置**：一次 Safe Browsing 全域名拉黑（可预防类第 1 名）、两个月模板死重、十余个对账提交，都源于 Day 1 少问了三个问题——"站上放什么""作品有多少""部署在哪"。开发者侧的真实失误集中在交互实现选型（button+window.open）与布局靠猜不靠量测，均已被后续测试钉桩覆盖。流程侧教训是多会话并行改同一仓必须按 hunk 核对归属。文档侧：HANDOFF 引用的 pm/qa/review 路径已全部失效，复盘时不可再依赖。
