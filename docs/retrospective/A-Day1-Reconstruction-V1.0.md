## 一、当前产品真实形态

### 1.1 一句话概括

**【核实】** 一个纯静态、无登录、无数据库、无留言、无后台的中文优先个人展示站（带中/英切换）。单页长叙事 + 每件作品的独立详情页；37 件作品以卡片墙呈现，可按形态筛选，卡片直接跳转到“成品本身”（在线站/下载页/GitHub）；三套主题；微信二维码、GitHub、YouTube 三个联系入口；同一份源码同时发布到 GitHub Pages（对外主地址）与 Vercel（镜像）。

### 1.3 与文档不一致的地方（已核实）

1. **作品数不一致**：`README.md` 与 `README.en.md` 写“35 个（18 网页 / 11 移动 / 3 桌面 / 3 方法与体系）”，实际 `app/content.ts` 是 **37 件（19 / 12 / 3 / 3）**。
2. **出口数不一致**：README 写“15 件在线站、8 件安装包、12 件退回仓库”，实际字段统计为 **23 件 `siteUrl`、3 件 `releaseUrl`、11 件无站无下载**。
3. **详情页“可达性”不一致**：README 说“每个作品有独立详情页”，但 **首页/卡片没有任何指向 `/projects/...` 的链接**（`out/index.html` 中匹配 `href="...projects/..."` 为 0 条；`app/ProjectGallery.tsx` 未引入 `next/link`）。详情页只保留为可直接输入地址的存档页，访客正常浏览无法到达。**【核实】代码与构建产物层面成立；【推断】这是 2026-10-03“卡片只放成果、不要项目档案”决定的副作用，未在 README/测试中描述为用户可见路径。**
4. **测试断言与文档同步但未覆盖数量**：测试钉住了“全部（37）”和具体标题，却未钉住 README 的 35/15/8/12，导致文档静默腐烂。

### 1.4 产品形态的推断（无用户签字）

- **【推断】** 当前 37 件作品、四类形态、双语、三主题是长期累积结果，不是 Day 1 就能准确预判的最终形态。
- **【推断】** 访客的主路径事实上是“看卡片 → 点外部成品/GitHub”，而不是“读站内项目档案”；详情页承担的是 SEO/存档/口头分享直达，不是主浏览路径。
- **【推断】** 站长日常维护成本主要落在“三处同时改”：`content.ts` 中文内容 + `i18n.ts` 英文标题摘要 + `i18n.detail.ts` 英文长文；漏一处测试会失败。这是后期双语带来的结构性成本。
- **未核实**：用户是否对当前三主题、双语、37 件作品、无详情入口的最终形态做过明确签收。历史 HANDOFF 只记到“2026-10-03 待用户签收三主题”（`docs/handoff/HANDOFF.md`），之后没有签收记录；不能把“已推送上线”当作“用户已满意”。

## 二、完整使用旅程

### 2.1 访客视角（桌面）

1. 从 GitHub Pages 主地址进入（国内更快）；Vercel 为备用镜像。
2. 首屏看到站名“后翻学长·记”、五个锚点（关于我/项目/兴趣/专题/联系）、语言切换、主题切换；右侧头像与三条标签、座右铭。
3. 向下滚过“当下”条，进入 01 我的经历（三段：军校学习 → 体制内工作 → 自由探索）。
4. 到 02 AI 项目作品：先看到筛选条“按形态筛选：全部（37）/网页应用（19）/移动应用（12）/桌面工具（3）/方法与体系（3）”，右侧“当前显示 37 个作品”；下方 4 列卡片墙（1440×900 下一屏可见 8 张）。
5. 每张卡片只有：封面、`2026 · 形态`、标题、三行截断摘要、两个按钮（“打开网站”或“下载应用”+“GitHub”）。点按钮在新标签打开外部成品/仓库；**卡片本身、标题、封面都不进站内详情页**。
6. 继续 03 兴趣切片：生活类 4 张（咖啡/阅读/吉他/AI 编程）、运动类 5 张（健身/篮球/抖舞/滑雪/冲浪），真实照片；缺图会显示占位框。
7. 04 经历与认证 9 条（含“备考雅思/备考认证”等如实表述，不改写成已获得）。
8. 05 曾研究的专题 4 张（健康与长寿、定投投资与保险、控糖饮食、孩子近视预防），只有标题与装饰，不展开文章。
9. 联系方式：微信（点开二维码弹层，Esc 或点遮罩关闭）、GitHub、YouTube。
10. 任意时刻可切中文/EN、切三主题；选择写入浏览器，下次打开保持；切换不丢滚动位置之外的业务状态（本站无业务状态）。

### 2.2 访客视角（手机）

**【核实】** ≤760px 时页头改为可换行：站名 18px、导航 12px、主题/语言按钮 11px；作品 1 列；兴趣分组改为两列布局；无横向滚动（历史多次实测记录在 `docs/handoff/HANDOFF.md` 2026-10-03 与 2026-10-07 条目）。
**【推断】** 页头同时容纳 5 个导航项 + 主题三选项 + 语言两选项，在 390px 宽会显得拥挤；这是“导航 + 两个全局开关都塞页头”的信息架构代价，Day 1 若只声明“手机上要好点”，很难避免后续微调。

### 2.3 站长（内容维护者）视角

1. **改文字/加作品**：只改 `app/content.ts`；加一条要填 `slug/title/status/statusLabel/year/category/summary/cover/tags/role/background/challenge/solution/outcome/gallery/links`，按实际有无填 `siteUrl`/`releaseUrl`/`repoUrl`。
2. **加英文**：同一件作品还要在 `app/i18n.ts` 补标题+摘要、在 `app/i18n.detail.ts` 补 role/background/challenge/solution/outcome/tags；测试会检查“每个作品都有英文块、字典无多余项”。
3. **配图**：封面放 `public/projects/`（约 16:9）；生活照按固定文件名转 WebP 放 `public/photos/`，原图备份到 `assets/photo-originals/`；头像改动需重新生成 `app/profile-inline.ts`（base64）。
4. **发布前**：`npm test`（构建 + 14 条断言）+ `npm run lint`；确认外链真实可开、私有仓名不出现、没有编造链接。
5. **发布**：commit + push `main`；GitHub Actions 构建 Pages 子路径版本，Vercel 自动构建根路径版本；不需要登录平台后台。
6. **发布后核验**：打开 Pages 地址抽查（Vercel 域名在本机网络常不可达，历史记录只能 `vercel ls` 看状态）；核对新卡片、筛选计数、主题/语言、图片 200。
7. **日常巡更**：项目仓库改名会产生死链（2026-10-03 一次修 4 条）；外部站点会失效（Vercel/Coze/ChatGPT 临时域名）；平台风控会扫全站（2026-10-23 Google Safe Browsing 把整域判“欺骗性内容”，只能下架服务卡）。
8. **文档维护**：README/README.en 的数量与出口分布需手改，已出现 35 vs 37 漂移；HANDOFF 也要手写。

**站长旅程的关键结论**：这不是“写完就完”的静态页，而是**一个需要持续录入作品、维护双语、核对外链、盯平台风控的小型内容系统**。Day 1 若不说明“以后会不断加作品/可能双语/外链会变”，实现方案很容易做成一次性硬编码。

## 四、关键 UI / 信息架构

### 4.1 结构（已核实）

- **单页 + 锚点导航**：五个一级区块用编号 01–05 标记；联系方式不编号但独立成段。页头导航就是这五段，没有二级菜单、没有侧栏、没有面包屑。
- **首屏是“人”而不是“作品列表”**：大字号姓名、三条标签、座右铭、简介、头像。作品在第二屏之后才出现。这决定了它是“个人名片”而不是“作品集目录”。
- **作品墙是主页面的重心**：筛选条 + 计数 + 4 列卡片；卡片信息层级固定为封面 → 年份·形态 → 标题 → 3 行摘要 → 两个成果按钮。
- **卡片不承担站内导航**：没有“详情/档案”入口；按钮语义是“成品本身”（打开网站/下载应用）与“源码”（GitHub）。
- **详情页是独立文档页**：顶部返回项目列表 / 站名 / 语言切换；正文固定四段“背景、挑战、方案与过程、成果”。它是“档案”，不是浏览主路径。
- **联系区是三个编号入口**：01 微信（弹层二维码）、02 GitHub、03 YouTube；没有留言表单、没有邮箱。
- **空状态有设计**：没有已发布作品时显示“项目档案，正在形成”与三个待发布槽位（`HomeView.tsx` 中 `project-empty`），目前因 37 件而不会出现，但保留了首次上线时的形态。

### 4.2 可复用的界面经验

1. **一屏密度要用真实尺寸量**，不能靠“看起来差不多”。历史记录：8 件作品时把 3 列改 4 列、去掉 `min-height/padding`、封面 16:9、标题 26→20px、摘要 3 行截断，实测 1440×900 与 1280×800 都是 4 列 2 行、8 件一屏全见（`docs/handoff/HANDOFF.md` 第 6 条）。
2. **筛选条的“计数”必须钉在固定位置**：`.filter-row { flex: 1 1 0; min-width: 0 }` + `.filter-count { flex: 0 0 auto; white-space: nowrap }`，否则 27→3 的位数变化会在临界宽度把计数挤到下一行（`9f4389d`，`app/globals.css` 642–650 行）。
3. **主题切换要有防闪白脚本**：`layout.tsx` 在 `<head>` 读 `localStorage.theme` 并白名单校验；新增主题必须同时改 CSS 块、脚本白名单、`THEMES` 数组三处，漏一处首屏会闪回默认深色（HANDOFF“新增主题的固定流程”）。
4. **语言切换不能要求服务端感知**：静态导出下服务端永远出中文，客户端挂载后按 `localStorage` 切 `<html data-lang>`；详情页没有切换按钮也要继承语言（`LangBootstrap`）。
5. **图片策略分级**：首屏头像 eager/内联，非首屏兴趣图 lazy；缺图用占位框而不是 alt 文本破图。
6. **a11y 不是装饰**：跳过链接、语义标题、`aria-pressed`、弹层焦点、Esc 关闭、`prefers-reduced-motion` 关动画（`globals.css` 1701 行）。

### 4.3 已发现的界面/架构风险

- **详情页孤儿化**（见 1.3 第 3 条）：如果仍希望访客读到“背景/挑战/方案/成果”，Day 1 就要决定“卡片是否留一个文字入口”。当前状态是：测试仍在维护 37 个详情页，但主路径不消费它。
- **手机页头拥挤**：5 个导航 + 3 个主题项 + 2 个语言项同时存在；760px 以下导航 12px、开关 11px（`app/globals.css` 1504–1528 行），低于现行全局“正文不小于 15px”的要求。**【核实】样式值成立；【推断】实际观感与可读性需真机核验。**
- **作品计数写死在多处**：筛选计数自动算，但 README 数字、测试里的“全部（37）”与目录清单都是手写；加作品时必须同步，否则测试失败或文档失真。

## 五、V1 必须有 / 明确不做

### 5.1 V1 必须有（缺一项就不能算可交付）

1. **一个真实的“我是谁”首屏**：姓名/昵称、地区、三条自我标签、一句座右铭、一段简介、一张真人头像（可先占位）。
2. **三段真实经历**（时间 + 标题 + 一句说明），按事实写，不包装成简历。
3. **作品墙从第一版就要有“真实出口”的字段**：每件作品能填“在线站 / 下载页 / 源码仓库”，没有就不填，不许编造；卡片按有无渲染按钮。
4. **作品卡的最小信息集**：封面、年份、形态、标题、3 行内摘要、成果按钮。
5. **按形态筛选 + 当前数量**：分类用访客听得懂的名字（网页/移动/桌面/方法与体系），计数随数据自动变。
6. **兴趣照片区**：固定文件名 + WebP + 缺图占位 + 生活/运动分组。
7. **经历与认证清单**：如实区分“已获得”和“在备考/入门”。
8. **专题清单**：4 个长期关注主题（只列标题即可）。
9. **三个真实联系方式**：微信二维码、GitHub、YouTube；没有的宁可不放。
10. **内容单一真值文件**：站长只改一个内容文件就能加作品/改文字，页面不散落硬编码。
11. **纯静态构建 + 一键发布**：不依赖数据库/登录/后端；push 即上线；能同时给国内与海外一条地址。
12. **404 页、页面标题/描述/分享图**（`layout.tsx` metadata + `public/og.png`）。
13. **基础响应式与可访问性**：桌面 4/3/2/1 列；手机无横向滚动；键盘可达、alt、跳过链接、减少动画。
14. **发布前自检**：至少能自动验证首页关键内容、37 个详情路由、图片随构建产出、404、外链仓库名、私有仓不露出、中英完整。

### 5.2 V1 明确不做

1. 不做登录、注册、数据库、留言、评论、后台、CMS。
2. 不做“站内编辑模式”或 `localStorage` 覆盖层改内容（历史上做过 `CategoryEditor`，被用户要求整体删除：纯静态站改内容应改真值文件 + push，见 HANDOFF 第 86 行）。
3. 不做求职简历式表达，不写“精通/已认证”等未经证实的措辞。
4. 不虚构项目、资质、联系方式、照片；没有上线站就不放 `siteUrl`。
5. 不挂第三方推广/代充值/中转服务卡（会带来平台风控与信任风险）。
6. 不同时维护三个以上部署平台；不自建域名/不做 ICP 备案（除非用户明确要自有域名）。
7. 不暴露私有仓库地址；私有项目只给官网落地页或标注“内测中”。
8. 不在没有 `npm test` 通过的情况下 push。
9. 不把个人高清原图、二维码源文件、临时截图、治理脚手架提交进公开仓库。

### 5.3 可延后（不属于 V1 阻断）

- 三套主题（先一套深色或浅色即可）。
- 中英双语（先中文，确认有海外读者再加）。
- 作品详情页长文（先在卡片摘要里说清；真要详情再补）。
- 国内第三方托管（EdgeOne/CNB/CloudBase）加速。
- 自定义域名、统计、RSS、sitemap。

### 6.2 必须人工/真机验收（测试替代不了）

3. **筛选**：逐个点 4 个形态 chip，卡片数与计数一致；在 761–1440 之间拖动窗口，计数不掉行。
4. **卡片出口**：至少每类抽 3 张，实际点开“打开网站/下载应用/GitHub”，确认 200 且不是死链/私有仓/平台已下线。

10. **文档一致性**：README/README.en 的作品数、出口分布与 `content.ts` 一致（当前已 35 vs 37 漂移，验收时应修）。

- **数量单一真值**：README 的数字改为从 `content.ts` 生成，或干脆不写具体数字，避免每次加作品都手改。

## 八、可直接给计划者的 Day 1 中文提示词

```text
我想做一个长期维护的个人网站，不是求职简历，也不是作品集罗列，而是“别人点进来能快速认识我、并且能直接用到我做的东西”的数字名片。请先帮我把它做成一个能上线的第一版，再谈加功能。

二、网站要有哪些内容（按这个顺序）
1. 首屏：我的人（头像、标签、态度、简介），不要一上来就是作品列表。
2. 我的经历：三段，按时间倒序或正序都行——军校学习、体制内工作、现在自由探索；每段一句事实描述，不要写成简历成绩。

6. 我长期研究的专题：健康与长寿、定投投资与保险、控糖饮食、孩子近视预防。只列标题，不展开文章。
```
